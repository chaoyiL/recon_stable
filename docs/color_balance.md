# 偏蓝诊断与调整记录

2026-11-02 对当前相机和 Arduino 灯带进行了实拍。目标是改善胶皮有效区域的颜色，同时保留四边彩色照明。调整已应用到当前设备和 `config.yaml`。

2026-11-03 图像接口已改为线性 RGB：采集图片和录像帧保存浮点 NPZ，所有原图预览直接显示线性值；不再提供 sRGB 显示切换或自动检查 PNG。下文实拍与图片产物是 2026-11-02 的历史记录，未重新采集或覆盖。

## 结论与依据

主要问题是当前灯光、胶皮和相机的组合响应偏蓝，4600 K 的固定白平衡不足以补偿；原曝光又使蓝通道大面积饱和。旧预览把线性数值直接当作显示编码使用，进一步加重可见的色偏和暗部压缩。

1. **未发现通道交换。** 低曝光下依次向全部灯珠发送纯 R、G、B，相机分别得到对应的主通道。串口按逻辑 RGB 传输；固件的 `NEO_GRB` 表示灯珠物理字节顺序，`Color(R,G,B)` 接收的仍是逻辑 RGB，符合 [Adafruit NeoPixel 接口](https://adafruit.github.io/Adafruit_NeoPixel/html/class_adafruit___neo_pixel.html)。
2. **白平衡确实生效，但单改色温不够。** 驱动回读自动白平衡为 0、色温为 4600 K。全部灯珠发送等 PWM 的 RGB，在曝光 10、亮度 5% 下，胶皮编码 RGB 均值约为 `(9.1, 13.1, 45.4)`；改为 6500 K 后为 `(16.0, 13.2, 29.5)`。蓝色明显下降，仍高于另外两个通道。等 PWM 不等于等辐射功率，这个实验测量的是整套系统响应。
3. **原图已经偏蓝并严重过曝。** 修改灯带前，按原相机配置曝光 130、4600 K 保存的基准原图中，测量区域约 97.3% 的像素蓝通道达到 250–255。饱和后的颜色信息不能靠软件白平衡恢复。该基准记录的是当时实际亮灯状态；固件没有颜色回读接口，不能据此还原用户此前在 GUI 内调整的每颗灯珠值。重新发送代码默认配色、整体亮度 100% 时，三通道均更严重过曝。
4. **没有证据表明四边顺序装反。** 分边点白光的影像响应位置与上、右、下、左一致；四边白光都偏蓝，不只是左侧纯蓝灯带影响。原默认总 PWM 为 `(1833, 2475, 2475)`，蓝与绿总量相等。侧边反射、胶皮透反射、LED 光谱和相机内部颜色处理仍会共同改变成像；现有实验不能把这些因素各自独立定量。外侧支架仍保留局部蓝色，符合本次优先胶皮、保留彩光的范围。
5. **显示约定影响观感。** BT.709 解码后的线性值直接乘 255 交给窗口，会压暗中间调并放大已有通道差异；它不会单独把中性灰变蓝。2026-11-02 实拍采用 sRGB 正向曲线显示；2026-11-03 按统一接口要求改为直接显示线性值。曲线依据见 [Linux 色彩空间说明](https://www.kernel.org/doc/html/latest/userspace-api/media/v4l/colorspaces-details.html)。计算继续采用 BT.709 逆曲线。

## 固定参数与处理链路

| 设置 | 当前值 | 用途 |
| --- | --- | --- |
| 灯带布局 | 上 9、右 4、下 9、左 4、空出 3 | 保留现有物理布局与四边配色 |
| 整体亮度 | 30% | 降低照度与过曝风险 |
| 灯带 `rgb_scale` | `[1.0, 1.0, 0.35]` | 输出时固定衰减蓝通道 |
| 相机曝光 | 20，V4L2 绝对曝光单位 | 当前设备对应 2 ms；减少通道裁剪 |
| 相机白平衡 | 手动 6500 K | 减少相机输出中的蓝色偏差 |
| 分辨率与格式 | 640×480、YUYV | 固定本次验证的采集模式 |
| 背光补偿 | 0 | 避免该 ISP 控件残留先前值 |

V4L2 格式实测为 `colorspace=8, ycbcr_enc=1, quantization=0, xfer_func=1`，其中显式 `xfer_func=1` 为 BT.709。没有更改已有图像解码曲线。曝光的单位依据 [V4L2 相机控件文档](https://docs.kernel.org/userspace-api/media/v4l/ext-ctrls-camera.html)。

灯带输出按 `int(逻辑 RGB × 单颗亮度 / 100 × 整体亮度 / 100 × rgb_scale)` 计算，空出灯珠始终熄灭。校正固定在照明输出端，不按每帧内容重新估计白平衡，避免把法向变化带来的颜色变化抹去。Arduino 协议和固件不需要改变。

`utils/camera.py` 对配置请求的 FOURCC、背光补偿、手动曝光模式和白平衡设置进行回读，失败释放设备并报错。`capture.py` 和相机标定入口传入同一套参数。独立的 `reconstruction/surface_reconstruction/run_reconstruction.py` 实时入口尚未接入这些设置。

## 实拍验证

测量区域固定为原图像素 `x=155:490, y=150:270`，位于胶皮内部，包含少量 marker；未用全画面支架代替胶皮统计。以 8 位通道值 `>=250` 定义“接近饱和”。最终每次重新打开相机，读取 20 帧，保存最后三帧的逐像素中值。

| 指标 | 修改前基准 | 最终配置，第一次重新打开 |
| --- | --- | --- |
| 编码 RGB 均值，0–255 | `(173.57, 200.32, 251.55)` | `(105.96, 89.69, 99.34)` |
| 解码线性 RGB 均值 | `(0.4864, 0.6434, 0.9816)` | `(0.1998, 0.1664, 0.1851)` |
| 线性 B/R 均值比 | `2.02` | `0.93` |
| 蓝通道接近饱和比例 | `97.30%` | `0.0075%` |

连续三次重新打开后，编码 R/G/B 均值分别落在 `105.63–105.96 / 89.69–89.98 / 99.07–99.50`。最终胶皮仍有左蓝、右绿和顶部偏红的空间变化；平均接近中性不表示整块胶皮应当处处相同。

原始帧、正确显示的预览、各轮实验 JSON 和对比图保存在本地 `assets/color_diagnostics/`，遵循仓库生成产物忽略规则：

- `baseline.png`：修改灯带前的原图。
- `probe.json`、`probe_low.json`、`probe_tune.json`：单色、分边、低曝光与参数扫描。
- `final_0.png`、`final_display_0.png`：最终原图与显示预览。
- `final_verification.json`：最终配置、ROI 定义和三次重新打开的统计。
- `comparison.png`：修改前后在相同显示编码下的对照。

## 启动、检查与限制

在仓库根目录分别运行灯带控制器和采集程序：

```bash
uv run python -m hardware.led_controller
uv run capture
```

控制器选择 Arduino 串口并连接，等到“已发送 29 颗”后查看采集窗口。启动时读取当前配置；按钮颜色表示逻辑色，固定输出校正另有文字说明。相机窗口直接显示线性值，按 `p` 保存线性 NPZ，按 `v/s` 开始或停止逐帧 NPZ 录像。

验证包括三次真实相机重新打开、Arduino 有效帧确认、预览曲线锚点、RGB 顺序、灯带校正和相机拒绝设置时的处理。执行 `uv run --no-sync python -m unittest discover -s tests`，98 项通过；本机测试期间 JAX 报告缺少 cuDNN 后使用可用后端，此次没有验证 GPU 重建性能。

调整照明、曝光和白平衡后，需要在新设置下重新采集无接触参考图、法向标定图，再重新生成颜色样本与 LUT；已有参考图和标定数据未覆盖。当前没有进行标准色卡或辐射定标，不能保证相机 RGB 与调色板数值逐项相等，也不能据此单独判定 LED 光谱、胶皮或相机 ISP 的责任比例。调整后的 gamma、gain 等其余 ISP 控件仍依赖设备当前状态，本次回读分别为 100、0。
